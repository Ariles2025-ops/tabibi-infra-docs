1. Cinq principes

Sécurité d'abord

Données de patients : Keycloak (OIDC, PKCE, MFA), JWT validé à chaque requête, autorisation par rôle puis par propriétaire, aucune donnée de santé dans les journaux ni les notifications.

Portabilité

JPA + Liquibase, images OCI, configuration par variables d'environnement : base et hébergeur remplaçables.

Testabilité

Chaque fonctionnalité arrive avec ses tests : domaine, service, tranche web, intégration PostgreSQL, Playwright pour le front (seul outil de test navigateur du projet), tests Flutter.

Clarté

Architecture hexagonale, un module par domaine, nommage en français, un commit par fonctionnalité, journal dans chaque dépôt.

Progressivité

Fonctionnalité par fonctionnalité, un serveur pour commencer, une voie d'évolution sans réécriture.

2. Vue d'ensemble

Cinq rôles (patient, médecin, secrétaire, pharmacie, administrateur), deux applications clientes (web pour tous les rôles, mobile pour les patients), un serveur unique derrière Caddy avec l'API, Keycloak et PostgreSQL, et Jitsi Meet pour la vidéo.

4. Architecture hexagonale du backend

Chaque module est découpé en domain/ (entités, règles, ports), application/ (cas d'usage) et adapter/ (contrôleur REST, repositories en mémoire et JPA). Le domaine ne dépend d'aucun cadre ; derrière chaque port il y a un adaptateur en mémoire (dev, tests) et un adaptateur PostgreSQL (profil postgres).

Les erreurs métier sont traduites en un seul endroit (GestionErreursApi) : 400 contenu invalide, 403 accès refusé à la ressource d'un autre, 404 introuvable, 409 transition d'état interdite, toujours avec le corps { "erreur": "..." }.

5. Modules et dépendances

Dix-sept modules regroupés par famille ; les dépendances passent par des ports (Notifieur, AlerteCreneau, RendezVousRepository) et ne forment aucun cycle.

7. Modèle de données

Seize changelogs Liquibase, dix-sept tables, clés uuid, dates timestamptz. Les identifiants de patients, secrétaires et pharmacies sont des sujets Keycloak : il n'y a pas de clé étrangère physique, les liens sont logiques.

8. Identité, jetons et autorisations

  • Authorization Code + PKCE pour le web et le mobile, clients publics sans secret, redirections explicites.
  • Jeton d'accès de 5 minutes signé par le realm ; l'API vérifie la signature (JWKS), l'expiration et l'émetteur.
  • Trois niveaux d'autorisation : chemin (SecurityConfig), rôle (@PreAuthorize), propriétaire (dans le cas d'usage).
  • Keycloak durci : force brute, politique de mots de passe, OTP, sessions courtes, realm de production sans comptes de démonstration.
  • Anonymisation des vues publiques, consentement explicite pour la vidéo, journal des accès sans corps de requête et avec IP tronquée.
Avant la production : conformité à la loi 18-07 (données personnelles, localisation), chiffrement au repos, sauvegardes testées, MFA imposée, test d'intrusion. Voir docs/SECURITE.md.

10. Front web et application mobile

Web (Angular 18)

Un dossier par domaine (service HTTP + composants standalone), auth/ (OIDC, intercepteur, rôles, gardes), configuration lue à l'exécution dans assets/config.json ; rendu côté serveur des pages publiques (@angular/ssr, server.ts) ; image Node qui écrit cette configuration et calcule la CSP au démarrage. 296 tests Playwright (39 dans node, 257 dans Chromium dont 19 parcours).

Mobile (Flutter 3)

Application patient : recherche, fiche et réservation, rendez-vous, ordonnances, notifications, téléconsultations, messagerie, avis, Dawini, listes d'attente, profil. Configuration par --dart-define, connexion AppAuth + PKCE, tests avec un FakeApiService.

Routes, gardes et structure détaillées dans docs/ARCHITECTURE.md ; liste fonctionnelle par acteur dans docs/FONCTIONNALITES.md.

11. Déploiement : commencer petit, grandir sans réécrire

Un VPS de 2 vCPU et 4 Go, Docker Compose, trois sous-domaines (front, api., auth.), certificats Let's Encrypt par Caddy, images tirées de GHCR, sauvegardes pg_dump quotidiennes.
