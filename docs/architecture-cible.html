La plateforme Tabibi, reconstruite pour durer

Une base technique professionnelle pour une application de santé : sécurité d'abord, testée de bout en bout, portable, et assez claire pour qu'une équipe recrutée la comprenne en une lecture.

01 — Fondations

Cinq principes qui décident de tout

Chaque choix technique de ce document découle de ces cinq engagements. Ils sont l'étalon : une décision qui les sert est bonne, une décision qui les contredit est rejetée.

🔒

Sécurité d'abord

On manipule des données patients. Authentification déléguée à Keycloak (OAuth2/OIDC), autorisation par rôle avec Spring Security, JWT signés, chiffrement en transit et au repos, journal d'audit. La sécurité est la première fonctionnalité construite, pas la dernière.

↔

Portabilité

Le métier ne connaît ni la base, ni le web, ni le fournisseur d'hébergement. JPA + Liquibase rendent PostgreSQL remplaçable ; les conteneurs Docker rendent l'hébergeur remplaçable. On démarre pas cher, on grandit sans réécrire.

✓

Testabilité

Chaque fonctionnalité arrive avec ses tests : unitaires (JUnit + Mockito), d'intégration sur une vraie base (Testcontainers), et de bout en bout. Un commit = une fonctionnalité + ses tests, pour tracer et revenir en arrière sans risque.

◇

Clarté

Architecture hexagonale, découpage par domaine, nommage explicite, documentation vivante avec diagrammes. Un développeur recruté doit comprendre l'application et son architecture sans qu'on la lui explique.

⟳

Progressivité

On avance fonctionnalité par fonctionnalité, doucement, chacune livrée, testée et documentée. L'application actuelle continue de tourner et d'assurer le lancement de décembre pendant que la nouvelle plateforme se construit à côté.

03 — Vue d'ensemble

Qui parle à quoi

Trois clients (web, mobile, et le back-office admin) parlent à une seule API. L'API délègue l'identité à Keycloak, persiste dans PostgreSQL, et confie les envois (SMS, e-mail, PDF, vidéo) à des services externes derrière des adaptateurs remplaçables.

04 — Back-end

Architecture hexagonale

Le cœur — les règles métier — est au centre et ne dépend de rien. Autour, des ports (interfaces) définissent ce dont le métier a besoin ; des adaptateurs les branchent au monde réel (web, base, services). Conséquence directe : on remplace PostgreSQL, un fournisseur SMS ou même le framework web sans toucher au métier — et on teste le métier sans base ni réseau.

Découpage par domaine

Le back-end est organisé en modules métier autonomes, pas en couches techniques fourre-tout :

  • identite — comptes, rôles, profils (s'appuie sur Keycloak).
  • annuaire — médecins, cabinets, spécialités, wilayas, recherche.
  • rendezvous — créneaux, réservation, agenda, statuts, listes d'attente.
  • ordonnances — création, consultation, PDF vérifiable.
  • teleconsultation — sessions vidéo, consentement.
  • dawini — demandes de médicaments, réponses des pharmacies.
  • messagerie & notifications — échanges, rappels SMS/e-mail.
  • administration — validation des médecins, modération, clés API.
05 — Sécurité

Identité, jetons et autorisations

Aucun mot de passe ne transite ni n'est stocké par notre API : Keycloak gère l'authentification (mot de passe, OTP SMS, MFA), et remet un JWT signé. Chaque appel à l'API porte ce jeton ; Spring Security le valide et applique les droits selon le rôle. Ni le web, ni le mobile ne voient jamais un secret durable.

Défense en profondeur. TLS partout · chiffrement au repos (base + stockage) · secrets hors du code (variables d'environnement / coffre) · journal d'audit des accès aux données sensibles · principe du moindre privilège · limitation de débit et captcha sur les points publics.

08 — Organisation Git

Une organisation, des dépôts clairs

Une organisation GitHub Tabibi (logo + branche main protégée), et un dépôt par brique — comme demandé. Chaque dépôt a sa propre CI et ses tests.

Dépôts

  • tabibi-backend — API Spring Boot
  • tabibi-web — front Angular
  • tabibi-mobile — application Flutter
  • tabibi-infra-docs — Docker, déploiement, documentation vivante (ce document + diagrammes)

Règles de la branche main

  • Pas de push direct — tout passe par une Pull Request.
  • CI verte obligatoire (tests + build) avant fusion.
  • Revue requise ; historique linéaire (squash).
  • Un commit par fonctionnalité, avec ses tests — pour tracer et revenir en arrière.

Convention de commits (traçable, lisible) :

feat(rendezvous): réservation d'un créneau + garde "créneau libre"
                  ├─ tests unitaires (cas d'usage)
                  └─ test d'intégration (Testcontainers + PostgreSQL)

fix(securite):    refuser un JWT expiré sur /ordonnances
docs(archi):      diagramme de séquence de la réservation
09 — Qualité

10 — Déploiement

Démarrer petit, grandir sans réécrire

Tout est conteneurisé (Docker) et « 12-factor » : configuration hors du code, sans état, prêt à changer d'hébergeur. On commence sur un serveur simple et abordable, on migre vers du managé quand le trafic le justifie — sans toucher au code.

Étape 1 Économique

Un VPS en UE / Francfort (Hetzner, OVH…) : Docker Compose lançant PostgreSQL + Keycloak + l'API + un reverse proxy (Caddy/Nginx, HTTPS auto). Le web et le mobile pointent sur le même domaine d'API. Coût faible, tout maîtrisé.

Étape 2 Managé & scalable

Base managée (PostgreSQL managé), API sur un service de conteneurs ou Kubernetes, Keycloak managé, stockage objet. Comme l'app est conteneurisée et portable, la bascule est une affaire de configuration, pas de réécriture.

Résidence des données Hébergement UE (Francfort) — cohérent avec le choix actuel, bon pour la latence depuis l'Algérie et pour la conformité des données de santé.
